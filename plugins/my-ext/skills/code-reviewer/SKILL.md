# Java Code Reviewer

对 Java 项目的变更进行多维度只读审查。简单局部改动默认内联；需要分工时，由主会话复用现有 `code-review` 审查执行者，分别审业务逻辑与代码风格，再复核汇总。

**执行边界**：不修改代码、不创建报告文件、不自动修复，不运行测试或构建；仅使用宿主已允许的只读查询、搜索与读取能力。只有主会话/顶层运行可以选择委派模式并组织分工；已受委派者（包括读取本文件的 `code-review`）直接执行交付维度，不再次派发、不递归加载本 Skill；未指定维度时执行全维度。

## Phase 1 — GATHER（收集变更 + 探测技术栈）

### 1.1 获取变更

先确定用户要求的是工作区变更、仅 staged、显式提交区间还是指定路径；不将这些范围混用。默认审查未提交工作区变更时，合并已跟踪变更与未跟踪新增文件：

```bash
git diff --no-ext-diff --no-textconv --name-only HEAD
git diff --no-ext-diff --no-textconv --stat HEAD
git diff --cached --no-ext-diff --no-textconv --name-only
git ls-files --others --exclude-standard
git rev-parse --abbrev-ref HEAD
```

- 按路径去重，排除生成物/第三方依赖；对范围内未跟踪源码使用文件读取工具（Read）读取全文，按新增文件审查，不能只看 diff。
- 指定文件/目录时，只收集该路径范围内的变更与新增文件（Git 命令用 `-- <路径>` 限定）；仅 staged 或显式 `<base>..<head>` 时只审对应内容，不混入未跟踪文件或其他工作区修改。调用链文件可作上下文，不自动扩大报告范围。
- 禁止为获取 diff 自动执行 `git add`（含 `git add -N`）。只有当前范围的已跟踪变更与适用的未跟踪源码清单均为空，才输出“没有待审查的变更”。
- 平台权限不允许上述命令时，不绕过限制：用已允许的 status 与文件搜索/读取能力核对新增文件；无法完整枚举时标注范围缺口并请求用户提供清单，不能宣称无变更。下文“本次 diff”包含此处已纳入范围的未跟踪新增源码。
- 记录当前项目开发目录、明确基线（工作区 / staged / 提交区间，含路径限制）及变更文件清单；staged / 提交区间须读取对应版本，不能用当前工作区内容替代。审查期间或汇总前发现基线变化，指出受影响的文件与结论并重新核实；未核实部分标为待复核，不声称全覆盖，无需创建快照文件。

### 1.2 探测技术栈

审查前必须了解项目上下文，避免用不匹配的约定误报：

1. 用文件读取工具读取根目录和相关模块的 `AGENTS.md`，若存在平台专用规则文件则继续读取。
2. 递归搜索 `**/pom.xml`、`**/build.gradle`、`**/build.gradle.kts`，排除构建输出目录。
3. 在所有构建文件中搜索 `lombok`、`mybatis-plus`、`mybatis-spring`、`spring-boot-starter-data-jpa`。
4. 根据变更文件所属模块分别判定技术栈，不能只读取仓库根目录构建文件。

> **核心原则**：项目规则 > 依赖探测 > 通用规则。审查结论应与项目实际技术栈一致。

### 1.3 加载项目审查规约（KB，必做）

**判据来源**：本技能保留审查动作、分工和报告流程；Java 详细判据统一从 KB `backend/java/code-review-checklist.md` 及其引用加载，不在插件维护另一份规范正文。

1. 先加载 `kb-loader`，由其统一解析 KB 根、来源、项目与任务路由；不可用时走其对应分支，不自行另找根或读取其他平台配置。
2. Java 审查先读已解析 KB 的 `backend/java/index.md` 与 `backend/java/code-review-checklist.md`，再按交付维度读取其「规则来源」表指向的正文；通用评审和偏好通过 loader 路由补载。分工时主会话提供规范索引，各执行者仍须实际读取适用正文，不能把收到路径当作已加载。
3. 项目规则优先；先核实适用范围与例外，再判级。违反适用明文规则至少 WARNING，不因历史先例豁免新代码。
4. 报告列出实际读取的规范及未能执行的检查，不得只列清单不读正文。
5. KB 不可用时遵循 `kb-loader`：强制要求的规范未读到则暂停依赖它的符合性检查；未配置且无强制要求时可依据已读项目规则和源码继续正确性审查，明确未加载 KB。不得恢复插件旧判据、猜测阈值或宣称符合未读规范。

### 1.4 选择执行方式与分工（仅主会话/顶层运行）

- **内联**：默认用于简单局部改动，直接执行 Phase 2 → Phase 3，不为凑分工增加子代理。
- **分维度委派**：用户明确要求多维度并行，或跨模块/复杂逻辑且独立分工有价值时，复用现有 `code-review` 执行者，分别交付「业务逻辑」「代码风格」。启动前简短说明分工及独立上下文会增加读取和 token 成本。
- **按宿主能力派发**：先查宿主实际注册的对应审查入口和平台契约，不臆造工具名或代理类型。若入口是工作流 Skill 而非原生子代理，读取其平台契约与 [code-review 唯一源正文](../../agents/code-review/AGENT.md)，交给宿主已有的只读子代理能力执行；在 Codex 尚未加载契约时，按需读取 [Agent 适配说明](../../codex/agent-adapter.md)。资源链接相对本 Skill 安装目录解析，不相对用户项目工作目录；不能定位资源时报告缺口。不增加权限，也不把工作流 Skill 名机械用作子代理类型。并行模式下在同一轮发起互相独立的维度任务，不等待一侧完成后再启动另一侧。
- **能力不足**：能独立委派但不能并行时，可按相同分工串行执行并如实标注；无法委派且用户未要求独立审查时，可内联并说明限制。用户明确要求并行时，不得擅自降级为串行或内联；明确要求独立审查时，不得降级为内联。受委派者将能力缺口交回主会话；主会话无法满足要求时报告受阻并等待用户决定，不通过其他代理绕过访问拒绝或任务限制。

分工只改变执行归属，不降低覆盖。下表是插件的调度映射；主题的具体判据、强度、例外及示例由已加载的 KB 审查清单与专项规范提供：

| 审查主题 | 业务逻辑 | 代码风格 |
|---|---|---|
| 结构枚举与校验 | 枚举接口校验链并沿实际入口核对 | 枚举常量、字段、类、方法、import，反查常量语义与复用 |
| 分层与工程结构 | 追踪分层问题的行为、数据及权限后果 | 核对职责、依赖方向、声明完整性、结构用途与工具一致性 |
| 数据、异常、安全与深度逻辑 | 核对 ORM、事务、SQL 性能、并发、资源、终止、业务边界与根因修复 | SQL/映射文件的格式与项目布局；其他样式线索交对应项 |
| 质量、空值与复用 | 追踪空值/返回契约、共享状态和校验保障 | 核对方法内聚、重复逻辑、常量/枚举复用与结构复杂度 |
| 测试 | 核对行为/边界覆盖、隔离与回归证据，不执行测试 | 核对测试命名与项目测试代码风格 |
| 日志 | 核对关键失败可观测、级别、上下文及敏感信息 | 核对格式、参数写法、进出成对及框架一致性 |
| 命名、注释与文件格式 | 注释与行为矛盾的线索交主会话复核 | 读取命名、Javadoc 与格式正文后核对适用项及例外 |

两侧均须核实规则适用范围与例外。跨维度或难明确归属的发现不静默丢弃：记录证据和归属疑点交主会话裁决；同一位置的规范违规与行为后果在汇总时合并，不按分工重复计数。

### 1.5 委派输入与等待（仅分维度模式）

主会话先完成范围、项目及规范索引收集，再向各执行者传递同一份审查基线与各自维度：

- 任务背景/目标，PRD、设计/技术方案路径及关键约定；没有则明确标注缺失，不猜设计意图。
- 当前项目开发目录、审查基线（工作区 / staged / 提交区间及路径限制）、变更文件清单（含适用未跟踪源码）、关键调用链入口/线索。若宿主只提供固定 Git 查询而不能直接读取指定基线，可传入已获授权的对应补丁/可读导出材料；不得以此绕过文件访问拒绝或用户限制，也不得改用工作区 diff，材料不足则报告覆盖缺口。
- `审查维度：业务逻辑` 或 `审查维度：代码风格`，及 1.4 的分工边界；附本插件 `code-reviewer` 源文件的绝对位置，供执行者读取调度与取证动作，详细判据另从已解析 KB 加载，不重新运行编排。不要把整个编排任务交给只读执行者。
- KB 根及来源、项目标识（未命中则说明仅通用规范）、适用规范文件路径与主会话已读项；各自仍须按范围读取，缺失或不可访问遵循 `kb-loader` 的分支，不猜路径。
- 只读、不得再次委派/递归加载本 Skill、不测试/构建、不自动修复、不写报告文件；发现基线变化时标出受影响结论。
- 返回本维度的有证据问题与覆盖情况：每条含 `文件:行号`、触发条件/规则来源、影响、最小建议，区分已验证证据与待核实线索；附实际读取规约、对应结构枚举、已查/不适用/未执行项及原因。跨维度线索单列交主会话，不冒充另一维度已覆盖。

等待所有已启动分支完成或明确失败/取消/受阻，再进入 Phase 3；未返回不能当作「无问题」。主会话不重复做整份子任务，只针对候选问题、争议与覆盖缺口复核必要上下文。

## Phase 2 — REVIEW（逐文件审查）

**执行范围**：内联且未限定维度时执行下方全部适用项；受委派者只执行 1.4 映射到交付维度的检查与结构枚举，不因「多维度/全面审查」的总称再做另一侧。

**审查姿态**：以高级开发工程师的视角逐方法通读交付维度相关的变更代码，而不是只勾规范清单——代码风格侧还要主动识别分支间重复条件/重复取值、复制粘贴的组装逻辑、可提前计算或提取的公共部分；发现即按影响判级并给出重构写法。

### 2.0 结构枚举（先列出，再核实）

对范围内 Java 变更逐项列出本维度负责的声明和校验链，再按已加载的 KB 判断；不能凭通读后的印象报数：

| 对象 | 必做动作 | KB 判据入口 |
|---|---|---|
| 常量 | 列出字面值，全仓反查并核对语义与现有归属 | 审查清单「新增常量前反查同值」 |
| 字段 / 类 / import | 列出修饰符、注入、包层次及依赖，反查已有组件 | 审查清单「新增类/方法先判定层次」「声明完整性」 |
| 方法 | 列出签名、继承、访问修饰符和注释，核对命名/继承例外 | 开发规范「文档注释（Javadoc）」与命名专项规范 |
| 入参校验链 | 从 DTO/API 声明追踪到实际入口触发、分组、Service 与其他调用入口 | 审查清单「校验必要性与入参来源」 |

使用已允许的只读搜索/读取能力，不为枚举运行未授权脚本。报告列出实际枚举结果与来源，未查项不写零；与后续发现合并，不重复计数。

### 2.1 分层与工程结构

从变更入口追踪 Controller/Service/数据访问层，列出职责、依赖方向和实际结构用途。按 KB 审查清单「分层、ORM 与工程结构核对」及其引用判断；分层的行为后果交业务侧，结构规范交风格侧。

### 2.2 ORM / 数据库

按实际框架读取映射与 SQL，核对参数绑定、动态标识符来源、批量操作的真实实参、更新字段和事务边界；循环内调用追踪到数据库再定性。判据加载 KB 的数据访问、批量校验、实体更新、事务及 SQL 性能条目，不在本 Skill 固定 ORM 注解、批量阈值或索引结论。

### 2.3 异常与资源

检索 catch/错误转换并读取上下文，沿失败路径核对最终状态、日志、回滚和资源释放；不能只靠正则认定吞错。读取 KB 异常处理、失败可观测和资源归属判据，保留必要的调用链证据。

### 2.4 安全

从外部输入追踪到 SQL、日志、返回对象与外部调用，核对权限入口与参数来源；检索敏感词后区分真实凭据、变量名和示例，不在报告泄露值。按 KB 安全及项目专项规则判断，不以读取受限为由绕过权限。

### 2.5 质量、复用与健壮性

对变更方法列出独立职责、重复条件/组装、可复用查询与现有组件，核对空值/返回契约和校验入口。读取 KB 的代码质量、常量语义复用、工程结构与空值边界判据；建议不得改变已确认业务语义。

### 2.6 测试

只读对照变更行为与测试用例，记录正常/异常/边界等覆盖和回归缺口，区分单元与集成测试的隔离方式。命名与质量判据按 KB 和项目规则；检查测试源码不等于已运行。

### 2.7 日志

业务侧沿失败分支核对可观测性与敏感信息；风格侧逐条比对日志格式和适用例外。详细判据读取 KB `backend/java/logging-standard.md`，不在本文件复制级别、格式表或固定模板。

### 2.8 注释

逐个对照新增/修改声明的签名、继承关系、实际实现与注释，核对标签口径、流程说明、自包含性及已有完整注释的例外。详细规则和示例只读 KB `backend/java/development-standard.md`「文档注释（Javadoc）」及审查清单「注释符合规约」，不按旧模板的句数或注释密度直接定性；不把设计文档复述进代码注释。

### 2.9 命名与格式

分开列出公开方法、私有辅助、Mapper 与框架覆写方法，实际读取 KB 命名专项规则并核对强度与例外；文件结尾与空白按代码格式规范检查。报告给出所核方法/文件及规则依据，未改动的历史命名不扩展为批量整改。

### 2.10 深度逻辑覆盖

业务侧按 KB 审查清单「深度审查补充判据」追踪循环查库、事务副作用、并发交错、资源释放、终止条件、业务边界与根因修复；每个疑点落到具体输入/时序、调用链和结果。仅见模式名不定性，缺少依赖/计划/业务证据则列待核实。主会话核对本次适用主题的覆盖，不因分维度而遗漏跨项影响。

## Phase 3 — REPORT（复核汇总并输出报告）

主会话负责最终结论，不能直接拼接子报告：

1. 复读每条候选问题的代码上下文、相关调用链及引用规则，核实触发条件、影响与适用例外；排除不适用、误报和缺乏证据的断言。待核实线索单列，不充当已证实问题。
2. 按同一根因/触发条件合并重叠发现，保留必要位置与证据，裁决跨维度归属；意见冲突按证据核实，不按投票或子代理数量定性。
3. 统一按实际影响和适用规则定为 CRITICAL / WARNING / INFO，不由「业务/风格」标签决定等级。CRITICAL 必须修复并 BLOCK；适用明文规则违规至少 WARNING；其余改进建议 INFO。
4. 核对审查基线与维度覆盖，合并实际读取规约和结构枚举明细并逐条去重计数；某分支失败、未返回或基线变化未复核时明确列缺口，不以缺失分支为零问题/PASS。报告只在会话输出。

内联模式同样核实证据、去重并说明未执行项；受委派者返回自己维度的候选与覆盖，不代主会话作整体结论。

```markdown
## Code Review 报告

**分支**: <branch>
**审查基线**: <项目开发目录；工作区 / staged / 提交区间及路径限制>
**变更文件数**: <N，来自本次范围内逐条去重的文件清单>
**执行方式**: <内联 / 分维度并行 / 分维度串行；能力限制如实说明>
**维度覆盖**: <业务逻辑、代码风格各自已查范围；不适用/未执行项及原因、基线变化待复核项>
**加载规约**: <本次实际读取的规范文件；未加载到时注明缺失项与影响>
**结构枚举**: 新增常量 N 个（同值反查 M 处）、字段 N 个（缺修饰符 M 处）、类 N 个（层次不符 M 个）、方法 N 个、新增 import N 条；接口 N 个（约束注解完备 X / 缺失 Y / Service 残留手写 Z）

### CRITICAL（必须修复，BLOCK 合入）

| # | 文件:行号 | 问题（触发条件、规则来源、影响） | 已验证证据 | 最小修复建议 |
|---|-----------|--------------------------------|------------|--------------|
| 1 | Xxx.java:42 | ... | ... | ... |

### WARNING（应该修复）

| # | 文件:行号 | 问题（触发条件、规则来源、影响） | 已验证证据 | 最小修复建议 |
|---|-----------|--------------------------------|------------|--------------|

### INFO（建议改进）
```

## 边界条件

| 场景 | 处理方式 |
|------|----------|
| 已跟踪 diff 为空 | 按 1.1 核对当前范围适用的 staged 与未跟踪源码；仅清单均为空才终止，枚举受限须报告缺口 |
| `AGENTS.md` 不存在 | 继续检查平台专用规则；两者都不存在时仅依赖依赖探测和通用规则，并在报告开头标注“未检测到项目规则” |
| 变更文件 > 50 个 | 仅审查 `.java` 文件；跳过配置文件除非有安全关注 |
| 变更仅包含 `pom.xml` / `build.gradle` | 检查依赖来源、版本锁定和仓库配置；只有项目已有漏洞扫描器且实际执行后，才能报告已知漏洞 |
| 同时存在 Lombok 和非 Lombok 文件 | 按文件分别判定：有 `@Slf4j` 的用 Lombok 标准，没有的用非 Lombok 标准 |
| ORM 混合使用（JPA + MyBatis 同项目） | 两个 ORM 的规则都适用，在报告中标注每个文件使用的 ORM |
| 检测到 Kotlin 文件混在 Java 项目中 | 仅审查 Java 文件；提及存在 Kotlin 文件但说明不在审查范围 |
| 代码库没有测试目录 `src/test` | 按已加载规范核对测试是否适用、是否位于其他位置；报告实际覆盖缺口，不仅凭目录缺失判 N/A 或通过 |
| 变更包含生成代码（`target/`、`build/`、`generated/`） | 排除这些文件的审查，在报告中注明 |

## 注意事项

- 报告范围限本次变更及其直接引入的问题；未改动的调用链和规范文件可作为取证上下文，不扩展为无关存量问题审查
- 未改动且与候选问题或适用规则无关的文件跳过
- 发现 CRITICAL 问题时明确标注 **BLOCK**，建议修复后再合入
- 审查结论应与项目实际技术栈一致 — 探测到的框架和约定优先于通用规则
- 优先复用项目中已有的枚举、常量、工具类和业务异常，不重复造轮子
- 审查前按 1.3 解析并读取适用规范；走允许的不可用分支时注明未加载 KB，只以已读项目规则和源码为依据，不声称通过 KB 符合性检查
- 如果变更涉及多个模块，按模块分组输出审查结论
- 注释逐项对照真实签名与实现，并按 KB JavaDoc 正文判断详略和例外；不把设计文档复述进注释，不以同类文件的注释密度覆盖明文要求
