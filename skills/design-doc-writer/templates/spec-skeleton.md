# 设计规范（Spec）骨架模板

> 用法：superpowers-planner / feature-dev 写入 `doc/features/<yyyy-MM>/<feature-name>/<yyyy-MM-dd>-<sub-feature>-design.md`（`<yyyy-MM>` 为当前年月第一层目录，如 `2026-09`，`<feature-name>` 功能名目录在其下）前，必须按本骨架输出完整章节。某章节不适用时显式说明"不适用/无需"，不得省略整个骨架。
> 文档定位：Spec 面向**人审**（审阅导向）；实施计划(plan)面向 **agent 执行**，两份**独立成文、不混写**，plan 另按 `plan-skeleton.md` 输出。
> 提交约定：设计文档写入工作区后**不自动提交 git**，留待用户审阅；是否提交由用户决定。
> 语言约定：产出文档一律使用简体中文（正文、标题、注释、README、DDL 注释等）；代码标识符、命令、路径字符串保持原文。

```markdown
# <功能名称> 设计规范

> 状态：draft | active
> 当前版本：v1.x
> 最近更新：<yyyy-MM-dd>
> 关联 PRD / 参考文档：<路径>
> 文档定位：审阅导向（面向人审）；实施计划(plan)另文独立、不混写

**版本历史（变更记录规约）**：任何实质修订（含临时调整）必须**追加一行**并**递增版本号**，不得覆盖旧行；「当前版本」同步为最新行版本。主版本号用于方案/结构变更，次版本号用于局部修订与口径澄清。**澄清/草拟阶段（`状态：draft`）的修订不记版本变更** —— 不追加行、不递增版本号，版本历史表保持初始行、`当前版本` 保持初始号；文档定稿（状态转 active）后才恢复记账：

| 版本 | 日期 | 变更说明 |
|------|------|---------|
| v1.1 | <yyyy-MM-dd> | <本次变更摘要> |
| v1.0 | <yyyy-MM-dd> | 初稿：<初始范围摘要> |

## 1. 需求分析（为什么改）
- 原始需求 / 现状痛点：为什么现在要改（一两句话）
- 功能范围：一句话说明本次交付什么；字段清单、接口细节留给「接口定义」「数据模型」章节，不在此展开
- 关键讨论：有分歧/取舍时记录，无则省略
- 边界与护栏（不改什么 / 不做什么）：条目化列出本次功能的取舍，后续评审与迭代依赖这些约束
- 禁止事项：只写本项目/本功能特有的禁止项；SQL、命名、注释等 KB 通用规范不复述，统一写「实现遵循项目知识库」
- **粒度约束（MUST，写完逐条勾选）**：
  - 现状痛点 + 功能范围合计 ≤ 3 句；「边界与护栏」每条 ≤ 1 行，只写取舍结论、不展开理由；
  - 正文不得出现表名、字段清单、SQL、方案对比、字段口径——出现即说明放错章节（方案 → 第 2 章，字段与 SQL → 第 4/5 章）；
  - 「关键讨论」无分歧时整条删除，不写「无」。
  - 正例：`- 功能范围：新增报告详情、审计明细分页两个只读查询接口。`
  - 反例：`- 功能范围：新增两个接口，详情接口按 dataNumber 查 lmp_authority_audit_report 返回 report_content……`——表名与字段应放第 4/5 章。

## 2. 方案选择
- 考虑过的方案对比表（A/B/C）
- 选定方案及理由（理由与方案同处呈现）

## 3. 架构与设计（怎么改）
- 模块职责分配
- 调用链（改造前 vs 改造后）
- 关键设计决策
- 逐方法/接口的实现逻辑伪代码与 SQL 放在第 4 章对应接口下（见第 4 章「各接口就地伪代码/SQL」），本章不重复
- **来源可追溯（MUST，就地写明来源）**：方案与各接口伪代码中每个数据来源、已查对象/集合、Mapper/Service/注入、取值与空值/边界，必须就地写明它从哪来（如：复用某方法已查的 `allBuidling`、`selectLmpBuildingByBuildingNo` 补列带出的 `system_id`、handler 已注入的 `reportMapper` 直调），写明「调谁/读谁/取谁」；**禁止**「由实施者处理」「此处待定/后续再定」「见后文」等留白半句。写完自查：每个符号的来源与依赖可逐行追溯、无遗留待问项

## 4. 接口定义与 API 设计
- **按接口维度组织**：每个对外接口一节，接口内按「对外 API（路径、方法、签名）→ 请求 DTO → 响应 DTO」展开；DTO 只在首次定义处写全，其他接口以章节号引用，不重复定义
- **内部接口**（Service / Strategy / Mapper 等）：各一节，列方法签名；入参/出参引用对应 DTO 章节号
- **DTO 表口径**：字段 / 类型 / 来源或取值规则 / 说明；取值规则（SQL 表达式、`to_char` 格式化、枚举回填等）写在接口章节，数据模型章节不重复响应映射
- **码值字段**：按项目知识库的字典字段命名规范，同时返回中文 `xxx` 与码值 `xxxDictCode`（如 `reportStatus` / `reportStatusDictCode`）；模板只引用规则，不复述正文
- **枚举与常量**：单独收尾
- **各接口就地伪代码/SQL**：对外接口下写 Controller 调用逻辑；内部接口下写方法伪代码与 SQL；逻辑、SQL 与理由就地贴在一起，避免依赖源码行号与评审术语
- 无对外 API 时显式说明，只保留内部接口与枚举

## 5. 数据模型
- **表结构 / 字段说明**：按「**表名 + 表字段 + 每个字段的取值范围**」逐表列出（取值范围写清允许值/码值/是否可空/NULL 语义等）；**类型与长度以 DDL 脚本为准，此处不重复列**
- **字段映射**：如为 Excel/文件导入需求，须提供「Excel 列 → 表字段」映射表（Excel 列、表字段、转换方式，标注同名/类型转换/语义改名/丢弃）
- **DDL**：涉及建表、加列、改表时，DDL 脚本输出到 `doc/features/<yyyy-MM>/<feature-name>/sql/` 并在本文以**路径引用**（**脚本不内联**，只做路径引用；设计理由与口径就近说明）；如无需 DDL 则显式说明"无需 DDL"
- **DML**：涉及初始化数据、字典、码值映射时，DML 脚本同样输出到 `doc/features/<yyyy-MM>/<feature-name>/sql/` 并以**路径引用**（**脚本不内联**）；如无需 DML 则显式说明"无需 DML"
- **索引**：列出支撑本次查询/写入的索引；沿用现有则写明索引名，新增则写变更与原因

## 6. 非功能需求
- 幂等 / 并发 / 性能 / 数据一致性 / 安全（按需覆盖）

## 7. 错误处理
- 异常场景 → 错误码 → 用户提示

## 8. 影响面与回滚
- 影响的既有模块/表/任务
- 兼容性与回滚方案

## 9. 风险与待拍板（单列放明面）
- 需知悉/待拍板的风险、口径、假设逐条列出，注明待谁拍板/确认
- 注：仅真正待拍板的业务口径/假设留于此；伪代码中每个符号的来源、取数与依赖属「必须就地写明」项（见第 3 章「来源可追溯」），**不得**以「此处待定/后续再定/见后文」下放

## 10. 测试策略
- 单元测试范围
- 集成测试场景
- 验证命令（编译/测试命令，对接 feature-dev）

## 11. 验收标准
- [ ] 可验证的完成条件

---

## 与实施计划(plan)的分工
- 本文面向人审，供评审拍板；实施计划(plan)另文面向 agent 执行
- 本文给出设计逻辑与伪代码/SQL 及其理由；完整可编译实现代码、TDD 步骤、逐文件验证命令与验收由 plan 输出
- 两份独立成文、不混写：plan 执行时以 plan 为主入口、本文仅作背景资料
```
